# Authorization Decision API — Part 3: Example MCP Server ("Acme Docs")

Depends on Part 1. The showcase artifact for the feature proposal. Lives in `examples/mcp-authz-demo/`, self-contained, not part of any Go build or CI job.

## 1. Story

Acme runs an internal docs MCP server. Three users sign in through Authgear from an MCP client (Claude Code, MCP Inspector, or the bundled demo client) and see **different tools** and **different outcomes** — decided centrally by Authgear, changed live from the portal with no redeploy.

| User | Roles (via) | Permissions on `https://docs.acme.localhost` |
|---|---|---|
| alice | `docs_admin` (direct) | `docs:read`, `docs:write`, `docs:delete`, `docs:publish` |
| bob | `docs_editor` (via group `writers`) | `docs:read`, `docs:write` |
| carol | `docs_viewer` (direct) | `docs:read` |

Tools → required Scope: `search_docs`, `read_doc` → `docs:read`; `create_doc`, `update_doc` → `docs:write`; `delete_doc` → `docs:delete`; `publish_doc` → `docs:publish`.

## 3. Server behavior

- `GET /.well-known/oauth-protected-resource` → `{ resource, authorization_servers: [AUTHGEAR_ENDPOINT], scopes_supported: ["docs:read"] }`.
- Every MCP request: verify JWT via Authgear JWKS; `aud` must contain the Resource URI, else 401 with `WWW-Authenticate: Bearer resource_metadata="…"`.
- `tools/list`: one `POST /access/v1/evaluations` (client mode, `execute_all`) for all six scopes; return tools where **token scope ∋ scope AND decision = true**. The response is per-request, never per-connection, as MCP requires.
- `tools/call`:
  1. token lacks the tool's scope → HTTP 403 `WWW-Authenticate: Bearer error="insufficient_scope", scope="<scope>", resource_metadata="…"` (step-up).
  2. `POST /access/v1/evaluation`; `false` → tool result `isError: true`, text "Authgear denied `docs:delete` for carol (role grants: docs:read)".
  3. PDP non-200 or network error → deny with "authorization unavailable" (fail closed).
- Each decision is published to the Decision Console: time, user, tool, action, decision, PDP latency (from `Server-Timing`), cache hit/miss.

## 4. Decision Console (`/console`)

Single static page, no build step, light/dark aware. Live table via SSE; header tiles: decisions/min, allow ratio, p50/p95 PDP latency, cache-hit ratio. A **"Why?"** column links to the Role in the portal. This is the screen recorded for the proposal.

## 5. Seed and demo client

- `seed.ts` reads `AUTHGEAR_ENDPOINT`, `ADMIN_API_KEY_ID`, `ADMIN_API_PRIVATE_KEY_PEM` (local dev keys) and is idempotent: create-if-absent for Resource, Scopes (`allow_static_first_party_client_access` and `allow_dynamic_first_party_client_access` on Resource and Scopes so Claude Code via CIMD/DCR can request them), roles, group, users (password `Demo1234!`), role↔scope grants, and `addResourceToClientID` for the m2m client.
- `demo-client.ts --user bob`: authorization_code + PKCE with the static first-party demo client (loopback redirect, opens browser), then prints a table of tools listed and the result of calling each one. `--all` runs alice/bob/carol back-to-back for the recording.

## 6. README walkthrough

1. Start local Authgear (CLAUDE.md "Start local dev").
2. Paste `authgear.yaml.snippet`, run `npm run seed`.
3. `npm start`, open `http://localhost:4100/console`.
4. `npm run demo -- --all` → three different tool lists.
5. Live change: portal → Roles → `docs_viewer` → Permissions → tick `docs:write` → carol re-runs, `create_doc` appears immediately (cache invalidation).
6. Connect Claude Code: `claude mcp add --transport http acme-docs http://localhost:4100/mcp`.
7. "How it works" diagram (token scope ∩ PDP decision) and links to the spec.
